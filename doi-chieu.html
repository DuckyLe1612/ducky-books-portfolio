Working document · Ducky Books

Every VAT box, sourced and proved

A specification, not a description. Each row states the rule for that box, not just what the software happens to do: I wrote the rule first, in Vietnamese, with the chief accountant (a role Vietnamese law requires to be separately qualified, not just a title the practice hands out), and the code was built to follow it. When the software deliberately leaves a box blank, that refusal is a rule too, decided on purpose.

The return itself is Form 01/GTGT, Vietnam's standard return for VAT (value-added tax, a tax added to the price of most sales; New Zealand's equivalent tax is called GST), filed monthly or quarterly. Vietnamese tax law gives every box a number; accountants say "box 43", not "closing credit". I kept the numbers.

1. The mapping

In the table below, "input" means purchase invoices and "output" means sales invoices; "net" means the price before VAT is added. Sales are classified by the tax rate on each invoice line, not by the invoice: one invoice can land in three boxes.

2. Boxes the form computes

The tax office's own software computes them the same way. If my figure and theirs differ, one of us has a bug.

[27] = [29] + [30] + [32] + [32a]     revenue subject to VAT
[28] = [31] + [33]                    output VAT
[34] = [26] + [27]                    total revenue
[35] = [28]                           total output VAT
[36] = [35] - [25]                    VAT due before carry-forward

net  = [36] - [22] + [37] - [38] - [39a]

[40a] = max(0, net)                   payable this period
[40]  = [40a] - [40b]
[41]  = max(0, -net)                  credit not yet used
[43]  = [41] - [42]                   credit carried to next period

Two rules that must always hold

[25] can never exceed [24]. The code keeps [25] between zero and [24]: it will not let the deduction claim more VAT than was actually paid, because that would make the return false.

[40a] and [41] cannot both be positive. Both are calculated from the same one number, which is either positive or negative, never both, so the two boxes can never both come out positive.

3. Box [22] stays empty

Box [22] should equal box [43] of the previous return, a number this system already holds. Making the software fill it in automatically would take only a couple of lines of code.

The chief accountant types it, every period.

Why

The previous return may have been amended by hand after filing. What counts is the figure actually filed with the tax office, not this system's last calculation. Usually the two match; when they do not, auto-filling would quietly push an out-of-date number into a filed document, and the person who signs it carries that.

The software shows a reference figure beside the empty box: the closing balance of last period's input VAT account (the amount still recorded there at the end of the period).

Proudest part: what has to be true first

That figure only means something if, at the end of last period, an entry moved the input VAT balance into the "tax payable" account (the account that tracks what the business owes the tax office). Skip that entry, and the input VAT account still holds the whole period's tax: the balance looks plausible but is wrong, inflated by the amount that should have been moved out.

If that clearing entry is missing, the software shows no figure at all instead: it names which month or quarter still needs the entry. A reference number that might be wrong is worse than no number at all, because the accountant cannot tell just by looking whether it is right.

4. A real error caught

Box [32a] has no VAT column, so it looks like it should not count toward anything. The first version of the software treated it that way, and got it wrong.

That made revenue totals [27] and [34] too low, by whatever amount was sitting in [32a]. The tax payable figure stayed correct, because [32a] carries no VAT to begin with.

How it was caught. The chief accountant typed a figure into [32a] in the tax office's own filing software and watched [27] and [34] rise by that amount. About a minute.

Why it mattered. This figure is cross-checked against invoice records and the corporate income tax return. A short total is what an audit opens with.

The lesson: a check that only asks whether the return balances (whether the numbers add up) cannot see this kind of error. Only a second, separately built calculation, the tax office's own software, caught it.

5. Unclassifiable rates

A few invoices carry a VAT rate that does not match any of the three standard rates (0%, 5%, or 10%), usually because a tax office listing merged several rates into one row, or from a data-entry mistake.

The form has no "other rate" box.

OptionEffectVerdict
Drop the lineOutput VAT reported too low (under-declared) Rejected. Under-declaring tax is the one failure with a legal consequence.
Block the returnNothing filed until every unusual invoice is resolved Rejected. Filing deadlines are fixed. Not filing on time is not safer: it just becomes unworkable in the last week before the deadline.
Group into the standard band, warn loudlyTotals stay complete; the individual box may be wrong Chosen. The total is never short; the warning names the invoice number and the unreadable rate.

To guess which rate applies, the software checks the invoice's VAT amount against its net amount at each standard rate, accepting a match within one dong (Vietnam's currency): invoices round each line to a whole dong, so an exact match would fail even on perfectly correct invoices.

6. Deliberately not built

A newer box on the current form is empty.

The code records why, in a comment: no verified sample of the new file format exists, and guessing at the exact structure of a government document is not worth the risk of getting it wrong. An empty box that explains why is safer than one that looks complete but might be a wrong guess.

The pattern. Four times the right answer was to do less: not fill box [22], not show a reference it cannot vouch for, not drop a line it cannot classify, not fill a box it cannot verify. Automation was available each time, and I chose not to use it, each time for a named, arguable reason.

What I would bring: not making a system do more, but a defensible account of where it stops.
