Where each figure on the VAT return comes from, and what proves it

One statutory return mapped end to end: where each figure is read from, what happens on the way, which box it lands in, and the check that catches ledger and return drifting apart. What I would want if I inherited someone else's return.

A specification, not a description. Every row is built and running. The rules were written first, in Vietnamese, with the chief accountant; the code followed. A refusal to fill a box is a rule too, and it is in the table.

Form 01/GTGT, filed monthly or quarterly. Vietnamese tax law numbers each box, and accountants say the number out loud: "box 43", not "closing credit". I kept them.

1. The mapping

Sales are classified by the tax rate on each invoice line, not by the invoice: one invoice can land in three boxes.

BoxWhat it holdsRead fromRule on the way

[24]Input VATinvoices, direction = input VAT on the same invoices, plus import VAT in [24a].
[23a] [24a]Importstyped by the accountant From the customs declaration, not held by this system. Not guessed.
[25]Input VAT actually deductiblederived from [24] Defaults to all of [24]. Input VAT booked outside account 133 is subtracted here but left in [24]: still declared in full, only the deduction narrows.
[26]Sales not subject to VATinvoices, direction = output Net amount only, no VAT column.
[29]Sales at 0%invoices, direction = outputNet amount only.
[30] [31]Sales at 5%, net and VATinvoices, direction = outputSplit per line.
[32] [33]Sales at 10%, net and VATinvoices, direction = output The temporarily reduced rate is declared in the 10% boxes: the form has no separate box for it. A reduction annex is required alongside, and the software says so.

2. Boxes the form calculates itself

Not read from anywhere: arithmetic on the boxes above, and the tax office's own software computes them the same way. If my figure and theirs differ, one of us has a bug worth finding.

[27] = [29] + [30] + [32] + [32a]     revenue subject to VAT
[28] = [31] + [33]                    output VAT
[34] = [26] + [27]                    total revenue
[35] = [28]                           total output VAT
[36] = [35] - [25]                    VAT due before carry-forward

net  = [36] - [22] + [37] - [38] - [39a]

[40a] = max(0, net)                   payable this period
[40]  = [40a] - [40b]
[41]  = max(0, -net)                  credit not yet used
[43]  = [41] - [42]                   credit carried to next period

Two invariants, checked not hoped for

[25] can never exceed [24]. Box 25 holds only the VAT that can be deducted, a subset of box 24. The code floors it at zero and caps it at [24]: deducting more than the tax paid files a false return.

[40a] and [41] cannot both be positive. A period either owes VAT or carries credit forward, and both come from the same signed figure.

3. Box [22]: the one the machine refuses to fill

The row I would defend hardest in an interview: doing less was correct.

Box [22], the credit carried forward from last period, should equal box [43] of the previous return: a number this system already holds. Auto-filling it is a two-line change.

The software does not. The chief accountant types it, every period.

Why

The previous return may have been amended by hand after filing. What counts is the figure lodged with the tax office, not this system's last calculation. Usually they match; when they do not, auto-filling would quietly push a stale number into a filed document, and the person who signs it carries that.

The software shows a reference figure beside the empty box: last period's closing debit balance on the input VAT account. The accountant compares, then types.

The reference has its own precondition. The part I am proudest of

That balance means anything only if last period's VAT was cleared to the payable account. Without that entry the input VAT account still holds the whole period's tax: the balance is inflated, plausible and wrong.

So the software checks first. If the clearing entry is missing it shows no figure at all and says the entry is outstanding for that month or quarter. A reference that might be wrong is worse than none: the accountant cannot tell by looking.

4. The control that found a real error

Box [32a] holds sales that need no VAT declaration, so it has no tax column. Easy to read as "does not count", and the first version did.

Revenue totals [27] and [34] then came out short by whatever sat in [32a]. Tax payable stayed right, because [32a] carries no VAT. Nothing looked broken; every internal check passed.

How it was caught. The chief accountant opened the tax office's own filing software, typed a figure into box [32a], and watched [27] and [34] rise by exactly that amount. Settled in about a minute. The formula became [27] = [29] + [30] + [32] + [32a].

Why it mattered even though the tax was right. This revenue figure is cross-checked against the invoice records and the corporate income tax return. A quietly short total is the kind of thing an audit opens with.

The lesson: a check that only asks "does the return balance" cannot see this class of error. The return balanced perfectly while being wrong. Only a comparison against an independent implementation of the same rules caught it.

5. When a figure will not classify

Real invoices arrive with rates matching no standard band, from a tax office listing that merged several rates into one row, or entered oddly.

The form has no "other rate" box. Three options:

OptionEffectVerdict
Drop the lineOutput VAT under-declared Rejected. Under-declaring tax is the one failure with a legal consequence.
Block the returnNothing filed until every oddity is resolved Rejected. Deadlines are fixed. A system that cannot file is not safer, just unusable in the last week of the month.
Group into the standard band and warn loudlyTotals stay complete; the individual box may be wrong Chosen. The total is never short, and the warning names the invoice number and the unreadable rate.

The rate is inferred by testing the VAT against the net amount at each standard band, accepting a match within one đồng. Not decoration: invoices are rounded to whole đồng per line, so an exact test fails on ordinary documents.

6. Deliberately not built

A newer box exists on the current form. This software leaves it empty.

Not an oversight: the code records why. No verified sample of the new file format exists to check against, and inventing a schema for a document that goes to a government system is not a risk worth taking. Better an empty box with the limitation stated than a guess that looks complete.

The pattern across this page. Four times the right answer was for the software to do less: not fill box [22], not show a reference it cannot vouch for, not drop a line it cannot classify, not fill a box it cannot verify. Automation was available each time and turned down, each with a named reason someone can argue with.

What I would bring to a role like this: not the ability to make a system do more, but a defensible account of where it should stop.

Boxes and formulas read from the software's own return builder. No figures, client names or tax numbers of real businesses appear here. Legal references are quoted as the system records them, verified against the signed source documents when the rules were written; I would re-check them before relying on them today, not quote from memory.
